01 · What SKYCOT is

Role-based AI employees that improve through work.

SKYCOT builds role-based AI employees — agents hired into a specific job, given real work, evaluated by a human manager, and rewarded by adding what they learned to a reusable skill library.

Most AI tools generate outputs. SKYCOT employees improve through work.

02 · The core loop

Every run can produce a learned skill.

The defining capability is the closed loop from work to learning to next-run improvement. Every SKYCOT agent runs this loop.

Role
The agent is bound to a vertical (e.g. GTM Engineer) with a deny list, an allow list, a memory schema, and bundled skills attached at session-creation time.
Work
The agent performs real tasks — analysis, drafting, research — inside that vertical's safety boundary.
Pattern
Across at least three reinforcing observations, the agent's pattern-detection skill identifies a stable signal.
Skill
A propose-skill meta-skill emits a candidate to memory in pending_review state. Never auto-active.
Approval
The operator reviews the candidate and promotes it. One CLI call flips lifecycle state to active.
Reuse
The next agent turn whose context matches the skill's trigger conditions consults the new skill via the same query the runtime always uses.
Improved next run
The agent's output incorporates the learned pattern. The library compounds.
03 · Example

The GTM Engineer.

The first shipped role. The GTM Engineer is bound to eight bundled skills.

  • define_icp — defines or refines an ICP from product, market, known customers, constraints. Flags evidence gaps.
  • find_target_accounts — searches for candidate accounts matching the ICP.
  • research_company — per-account deep research: signals, pain hypothesis, fit scoring.
  • research_person — per-role persona research: responsibilities, buying signals, message angles.
  • generate_outreach — drafts personalized outreach using verified facts and role/company research.
  • analyze_campaign — ingests operator-reported campaign outcomes; surfaces what worked, proposes next experiments.
  • detect_gtm_pattern — surfaces repeatable patterns from at least three observations across distinct campaigns. Refuses single-instance claims.
  • propose_gtm_skill — the meta-skill. Converts high-confidence patterns into reusable learned-skill candidates queued for operator approval.
Safety boundary The vertical's manifest deny list blocks terminal, file_write, file_patch, and delegate_task. The GTM Engineer is draft-only by contract — no sending, no CRM updates, no destructive tool calls reachable.
04 · Real demo flow

Before. Learning. Approval. After.

The full GTM Engineer learning loop, recorded against real CLI surfaces. Two equivalent paths: deterministic for reproducible demos, or live for end-to-end LLM verification.

Before — a weak campaign

100 emails sent · 2 replies · 0 positive

The agent's diagnosis: generic productivity hook, no verified company signal, audience-flat (“everyone gets time back”), single demo CTA. The control variant landed at zero positive replies on one hundred sends.

Learning — pattern detected, skill proposed

Across three reinforcing variant cohorts (one hundred sixty-five sends total), the agent identified that leading with the agent-learning loop and audit-chain visibility lifted positive-reply rate to 6–8% on technical-founder targets — well above the zero-positive baseline.

The propose-skill meta-skill emitted a candidate: technical_founder_learning_moat_outreach. State: pending_review.

Approval — pending_review → active

The operator reviewed the candidate's scope, rule, and guards. One CLI call flipped lifecycle state to active. The skill is now in the catalog.

After — improved GTM output

The next agent turn that matches the trigger conditions (technical founder + agent-platform GTM hypothesis) consults the active skill. The output anchors in one verified company signal, leads with audit-chain framing, holds to under one hundred twenty words, single low-friction CTA. Projected uplift: +4–6 percentage points on positive-reply rate vs the generic control.

05 · The proof system

Every step produces verifiable evidence.

Role binding
Every session row records the bound vertical id; bundled skills are materialised into the skill table at session-creation time and are visible to the agent runner via the same query the prompt assembler uses on every turn.
Memory
Campaign outcomes, detected patterns, and skill candidates are vertical-namespaced and append-only. Candidates are immutable once written; superseded proposals get a new row.
Skill lifecycle
Every skill row carries a lifecycle_state column — draft, pending_review, active, rejected, archived. Illegal transitions are rejected at the storage layer.
Evaluation
Each vertical ships a fixture suite (ten fixtures for the GTM Engineer) with a deterministic rule-engine scorer plus an optional LLM judge.
LLM judge calibration
A three-cohort calibration corpus — argo_aligned, polished_but_less_grounded, weak — locks the judge ranking; integration tests assert the ordering.
Audit trail
Every CLI surface emits structured audit rows. The gateway surface is an HTTP mirror of the CLI; both write to the same SQLite store.
06 · Architecture

Two halves with clear roles.

Claude / Argo

  • builds and runs role-based agents
  • handles vertical manifests, bundled skills, vertical-namespaced memory
  • manages the full skill lifecycle (propose → review → promote → approve → active)
  • runs deterministic + LLM-judge evaluations
  • exposes everything via CLI and gateway HTTP
  • enforces the safety contract (deny lists, allow lists)

Codex

  • generates real GTM outputs at scale (multi-variant campaigns)
  • creates calibration data for the LLM judge (strong / medium / weak distinctions)
  • validates output quality across distinct cohorts
  • does the heavy producer work that the evaluation system grades

The two systems share the canonical fixture set. Codex outputs flow into the calibration corpus that the LLM judge is tuned against.

07 · Evaluation

Two layers, complementary.

Deterministic rule engine

Fast, free, runs on every commit. Validates structural rules: required substrings, forbidden phrases, hallucination detection, abstention checks. Misses semantic equivalence — a model that says “role-based AI agents” instead of “role-based agents” gets zero credit. Useful as a fast safety gate, not as a quality judge.

Live LLM judge

anthropic/claude-sonnet-4-6, opt-in. Six quality dimensions: evidence-awareness, specificity, safe-abstention, operational-usefulness, role-fit, non-generic-GTM-reasoning. A safety veto caps the score and forces verdict=fail when the agent commits a contract violation (must-refuse, external mutation, unjustified skill proposal).

Calibration

The corpus has three variants per fixture: argo_aligned, polished_but_less_grounded, weak. Hard CI lock: the judge must rank argo_aligned > weak AND polished > weak. Strict mode (opt-in) enforces the full ordering argo_aligned > polished > weak.

Why both: the deterministic engine catches obvious failures cheaply; the LLM judge catches semantic ones the substring engine can't see. Together they form a tight quality gate that's both fast in CI and meaningful for the operator.

08 · What makes this different

Six properties, all load-bearing.

  • Role-based. Agents are hired into specific jobs, not given open-ended chat.
  • Learning loop. Every run can produce a candidate skill; the library compounds.
  • Reusable skills. Promoted skills persist across sessions, are vertical-namespaced, and are version-tracked.
  • Human approval. No skill auto-activates. Operator review is mandatory.
  • Evaluation built-in. Every vertical ships fixtures and a judge. Quality is contracted, not assumed.
  • Safety-first execution. Manifest deny lists are enforced at runtime. The GTM Engineer cannot send, write files, or update CRMs even if asked.
