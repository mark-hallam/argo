**Root cause of B4/B5 (verified, code-grounded):**
- `docs/skycot/pricing/v1-tiers.toml` `[free]` → `max_workers = 1`,
  `max_actions_per_month = 100`, `features = ["provider_mock", …]`.
- Tier limits typed in `crates/argo-identity/src/tier.rs:105` (`max_workers: u32`).
- Per-tenant worker count + cap enforced in
  `crates/argo-store/src/tenant_quota_usage.rs` (`worker_count(tenant_id)` vs
  `max_workers`); `GET /api/v1/workers` for this tenant returns
  `count: 1, names: ["Soak04"]`.
- A CSRF-token-attached replay of `POST /api/v1/workers` got past 403 to a
  `400 bad_request` (field/`worker_draft`-shape validation) — confirming the
  endpoint is reachable and the SPA's 403 is the **authorization/seat gate**,
  not the `csrf_missing` red herring my own token-less probe first returned.

**Drift / meter / bleed watch (the actual point of this run):**
- **No meter drift, no count contradictions** in the single-teammate workspace:
  /team (12 actions wk) ≈ /audit (46 rows, $0.034) ≈ /billing (Soak04 $0.0344)
  are mutually consistent.
- **No cross-teammate bleed**: the only worker in the tenant is Soak04. Agent
  A's Soak01-03 never appeared on /team, /approvals, /audit, or /billing.
  (Note: the browser network buffer still held stale request URLs referencing
  Agent A's Soak03 worker id `019ec040-…` from the shared tab — that is a
  client-side request-log artifact, NOT a server-side roster/tenant bleed.)
- No perpetual spinners; no blocking console errors (only the pre-existing
  benign stale-waitlist-CSRF warning Agent A already documented).

**So: did accumulation hold?** Unanswerable through the demo entry point as
specified — the Free-tier 1-worker cap makes a 3-teammate workspace impossible
there. For the part that COULD be exercised (1 teammate, repeat runs), the
roster, billing per-teammate attribution, single "Actions this month" row, audit
hash chain, and probation re-hold were all correct with no drift or bleed.
**Recommendation:** to test true multi-hire accumulation, the workspace must be
on a tier with `max_workers >= 3` (Pro = 5, Enterprise = unlimited), OR the demo
provisioner must seed a higher worker cap. A secondary UX gap: the 2nd-hire
rejection surfaces only as a bare red "Forbidden" banner with no explanation
that the Free plan is capped at 1 worker / no upgrade prompt — worth a friendlier
"you've reached your plan's teammate limit — upgrade to add more" message.
