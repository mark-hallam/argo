# Wave-2 Accessibility Audit (WCAG 2.1 AA)

- **Date:** 2026-05-20
- **Auditor:** Wave-2 audit agent #1 (a11y)
- **Method:** static analysis of `web/` (rg + manual code review of key files)
- **Scope:** demo journey + key in-product pages — landing, compare, /, team, workers, workflows, audit, skills, hire, onboarding, settings, billing, retro, cohorts, signup/signin/verify, replay, action drilldown, auth check-email
- **Build state:** read-only — no code modified

## Overall verdict

**a11y score: 4.5 / 10**

The codebase shows strong intent in several places (Radix Dialog for modals, focus-visible utility classes on most buttons, MotionRoot wraps `(app)/` for prefers-reduced-motion, lang="en" set, `<aside>`+`<nav>` landmarks for desktop sidebar, live regions on hire wizard + Sonner toasts). But six load-bearing failures occur on the **most-visited surfaces in the demo path**:

1. The homepage (`/` Approvals) and `/team` use `<h3>` for the page title and have NO `<h1>` — the demo recording opens here.
2. The marketing landing + compare pages, plus the in-product BrandLoudHero on `/`, `/team`, `/cohorts`, run an **infinite shimmer + pulse animation with no `@media (prefers-reduced-motion)` guard**. This will be flagged by axe and is a literal WCAG 2.2.2 / 2.3.3 violation.
3. The Approvals search input and Audit search input have no `<label>` and no `aria-label`.
4. Auth signup + signin use a `<div className="field-label">` instead of `<label htmlFor>`.
5. No skip-to-content link anywhere in the app.
6. `--muted-foreground` text on `--background` measures ~4.4:1 — borderline below the 4.5:1 minimum for body text. 544 callsites.

These will all surface in an automated axe / wave scan and any of them would lose a procurement-tier a11y review.

## Single highest-impact fix

**Add `prefers-reduced-motion` to BrandLoudHero (`web/components/skycot/BrandLoudHero.tsx`).**

One file, ~6 lines of CSS, fixes a hard WCAG 2.2.2 + 2.3.3 violation across `/`, `/team`, `/cohorts` — three of the most-visited in-product surfaces. It also reduces the perceived motion on the entire demo background, which is the kind of thing both axe and a procurement reviewer will note. The change is purely additive (only kicks in for users who set the OS preference), so it cannot regress the demo visuals.

Recommended snippet:

```css
@media (prefers-reduced-motion: reduce) {
  .skycot-brandloud-shine,
  .skycot-brandloud-eyebrow-dot.is-pulse {
    animation: none !important;
  }
}
```

Add the same `@media` block to `web/app/landing/page.tsx` around the `land-shine` keyframe declaration (line 716–726).

### 4. Color contrast (2 findings)

- **`--muted-foreground` borderline** — `oklch(0.52 0.015 248)` (~#7d7d8b) on `--background: #fafaff` measures approximately **4.4:1**. WCAG AA requires **4.5:1** for body text. This is below threshold by one tenth. **544 callsites** of `text-[var(--muted-foreground)]`. WCAG 1.4.3 (AA).
  - Fix: bump lightness from 0.52 to 0.50, which moves the ratio to ~4.7:1. One CSS change in `web/app/globals.css:136` fixes 544 callsites at once.
- **`--muted-foreground` placeholder text** — same color used in 7 `placeholder:` callsites. WCAG 1.4.11 Non-text Contrast requires 3:1 for UI components; placeholders inside inputs should be visually distinct enough to read.

Working well:
- `--foreground: #1e1b4b` on `--background: #fafaff` measures **>15:1** — easily AAA.
- `--brand-primary` (violet ~#7c3aed) on white is 5.1:1 — passes AA for large text and UI components.
- Pricing/landing gradients use white text on gradient — visually OK but I'd recommend an axe scan of the actual rendered pixels rather than rely on token math.

### 5. Screen reader / landmarks (5 findings)

- **`/compare` no landmarks** — `web/app/compare/page.tsx` has no `<main>`, `<nav>`, `<header>`, or `<footer>`. Screen reader users cannot use landmark navigation. WCAG 1.3.1.
- **No skip-to-content link** — confirmed by `rg 'skip.{0,3}(to|link|content)' web/` returning only unrelated matches.
- **Mobile nav has no `<nav>` landmark** — `web/components/ui/NavDrawer.tsx:37-47` mobile hamburger trigger row is a `<div>`, not `<nav>` or `<header>`.
- **Worker overview h-order** — `WorkerPersonalityCard` h4 with no preceding h3 makes the worker detail page's section tree unreadable by screen-reader landmark navigation.
- **Landing top header** — `web/app/landing/page.tsx:788` correctly uses `<header>` + `<nav>` — good. But the inner `<nav>` has no `aria-label`, so it's announced as "navigation" with no name. WCAG 1.3.1 (mild).

Working well:
- Root layout uses `<main>` in AppShell (`web/components/skycot/AppShell.tsx:35`).
- Desktop sidebar is a proper `<aside>` + `<nav>` (`NavDrawer.tsx:81,93`).
- Landing + pricing have `<header>`, `<nav>`, `<footer>` semantic structure.
- Live regions cover async updates (hire wizard, worker overview, toasts).

### 6. Reduced motion (2 keyframe sources, 5 surfaces affected)

- **BrandLoudHero** — `web/components/skycot/BrandLoudHero.tsx:84,131` — two infinite animations (`skycot-brandloud-shine` 5s, `skycot-brandloud-pulse` 1.6s). No `@media (prefers-reduced-motion)` guard. Used on:
  - `/` (Approvals — homepage)
  - `/team`
  - `/cohorts`
- **Landing `.land-shine`** — `web/app/landing/page.tsx:716` — 6s infinite shimmer animation, no media query.

Also present:
- `web/app/landing/page.tsx:494,633` — short 0.18s transitions on `:hover` — these are below the 5s threshold + are interaction-triggered, so generally acceptable, but a strict reading of 2.3.3 would still guard them.

Working well:
- `web/lib/motion/provider.tsx:36-48` correctly wraps the `(app)/` route group with `MotionRoot`, which reads `useReducedMotion()` and swaps the motion vocabulary to zero-duration. Anything that calls `useMotion()` honors the preference automatically.
- `MotionConfig reducedMotion={reduced ? "always" : "never"}` propagates to all `<motion.div>` callers without per-callsite checks.
- The hire wizard CelebrationOverlay (`web/components/skycot/hire/CelebrationOverlay.tsx:31`) uses live-region status and motion vocabulary.

Caveat: `MotionRoot` only wraps `(app)/` and `(hire)/` route groups. Marketing pages (`/landing`, `/compare`, `/pricing`, `/customers`, `/changelog`) and auth pages do not get the motion provider, so any framer-motion `<motion.*>` on those pages would also bypass reduced-motion. The CSS shimmer is the bigger problem since it bypasses MotionConfig anyway.
