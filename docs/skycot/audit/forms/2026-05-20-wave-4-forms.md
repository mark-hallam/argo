# Wave-4 Audit: Form Validation Across the Web App

**Date:** 2026-05-20
**Auditor:** Wave-4 agent #1 (forms)
**Scope:** All forms in `web/app/` + `web/components/` — read-only.
**Demo deadline:** Tomorrow (CEO demo recording).

## Method

Five dimensions per form:
1. **VALIDATION SCHEMA** — zod schema / required-field marking / pattern + length checks.
2. **ERROR DISPLAY** — inline-next-to-field vs toast vs alert vs silent.
3. **DISABLE-WHILE-SUBMITTING** — submit button is disabled during in-flight request; double-click prevented.
4. **SUCCESS FEEDBACK** — toast / inline message / navigation on success.
5. **EMPTY / CANCEL HANDLING** — Esc closes modal; back-button doesn't break state; draft preserved on tab-out where appropriate.

Library inventory (`web/package.json`):
- `zod` v3.24.2 — installed
- `react-hook-form` v7.54.2 — installed
- **In actual use:** zod = **1 file** (`web/lib/auth/signup-schema.ts`). react-hook-form = **0 files**.

Every other form rolls its own validation with `trim()` / `.includes("@")` / `>= N` checks. There is no centralized validation strategy. That is the headline finding.

## Top 5 worst-offending forms

These are ranked by likelihood of breaking on a demo viewer's first try, weighted by where the CEO is most likely to click.

### 1. Settings → Members invite modal (`web/app/(app)/settings/members/page.tsx`)

- Schema: ✗ — only checks `inviteEmail.includes("@")`. `foo@` and `@bar` pass.
- Inline errors: ✗ — never surfaces validation feedback.
- Disable-on-submit: ✗ — there is **no submit**; the button calls `setShowInvite(false)` then resets state. **No API call. No invite sent.**
- Success feedback: ✗ — modal silently closes; no toast; no member appears in the list.
- Esc / cancel: ✗ — no `onKeyDown="Escape"` handler. Overlay-click closes (good), but Esc does not.
- **Impact on demo:** If the CEO opens "Invite teammate" and sends an invite, nothing happens and there's no error. Worst kind of broken: silent.

### 2. Workflow Builder — Propose prompt + Save/Publish + Test run (`web/app/(app)/workflows/[verticalId]/[name]/build/page.tsx`)

- Schema: ✗ — `trim()` only.
- Inline errors: ✗ — only sonner toast on stubbed success.
- Disable-on-submit: ~ — there is a `proposing` boolean BUT it's tied to a `setTimeout(1400)`, not a real fetch. Real wire-up does not exist (the file's own comment says "PR #1882 rebase pending").
- Success: toast fires "Proposal ready" with hard-coded "1 step change proposed" — does not modify the canvas.
- "Edit step" button in the side-panel has no `onClick`.
- "Add step" button has no `onClick`.
- **Impact:** This is the flagship "AI workflow builder" surface. The CEO will likely click Propose. They will see a toast that promises a proposal. The canvas does not change. The "Edit step" button does nothing. Demo-credibility-killer.

### 3. Worker Settings Save buttons — Channels / Quiet hours / Budget / Autonomy / Approval-policy (`web/components/skycot/worker/settings/*.tsx`)

- Schema: ✗ for Channels/Quiet hours; ~ for Budget; ✓ for Approval-policy.
- Inline errors: ✗ across all five — even Budget's `aria-invalid` doesn't render a message.
- **Disable-on-submit: BROKEN PATTERN.** All five compute `disabled={!isDirty}`. They **do not track an in-flight save**. A user who clicks Save then re-clicks (or hits Enter twice) fires the optimistic patch twice. The second patch happens against the same baseline, so it overwrites itself. The cache then settles to whatever the server returns last.
- Success feedback: ✗ — none. The form re-syncs `value.start` etc. via `useEffect`, so it just looks like the form "took". No toast. No "Saved 14:32" timestamp.
- **Impact:** All five sections live on the most-likely-to-be-demoed page (per-worker Settings tab). Quiet click → click Save → nothing visible happens. Operator wonders if it saved. That's the demo failure mode.

### 4. Hire Step 4 — Adjust drawer (`web/components/skycot/hire/AdjustDrawer.tsx`)

- Schema: ✗ — trim-only.
- Inline errors: ✗ — Save just disables on empty text; no error message ever shown.
- Disable-on-submit: ✓ `saving` boolean.
- Success feedback: drawer closes; new draft appears via parent's redraft mutation. Good.
- Esc: ✓ via Radix Dialog.
- **Impact:** Lower than #1–#3. But it's on the hire-funnel demo path. Empty save click is silently noop-ed; better to surface "tell me what to change" hint like Step 1's pattern.

### 5. Worker → Add Fact dialog (`AddFactDialog.tsx`) + Worker → Add Responsibility Step 1 + a few "trim-only" textareas

- Schema: ✗ — trim-only.
- Inline errors: ✗ for #20; ✓ for #21.
- Disable-on-submit: ✓ both.
- Success feedback: ✗ for #20 (closes silently); ✓ for #21 (CheckCircle "Added").
- **Impact:** #20 (Add Fact) silently absorbs the input. If the CEO teaches the worker a fact, they get no confirmation that it landed. Trust-erosion at the exact moment that should be a wow.

## Single highest-impact form to fix before demo

**Worker Settings Save buttons** — Channels, Quiet hours, Budget, Autonomy, Approval-policy sections (collectively, 5 cards inside `web/app/(app)/workers/[workerId]/settings/page.tsx`).

Why:
1. **It is the most-likely-to-be-demoed surface.** The CEO will hire a worker on camera, then click into the worker to show off the settings — that's the natural narrative beat. Approvals, autonomy, budget caps, quiet hours: every one of these is a marketing-page promise.
2. **The brokenness is uniform across all 5 cards.** A single 30-line refactor — wrap each `onSave` in a `useMutation`-style state and bind both `disabled` and `loading` to the in-flight flag, then surface a single shared "Saved 14:32 · undo" toast on success — fixes all five.
3. **The current behavior is the worst possible UX shape: silent.** No error, no confirmation, click → click again → nothing happens visibly. Recordings of this look broken even when the underlying mutation succeeded.
4. **The fix is read-mostly:** no schema authoring, no copy revision, no design lock — just lift the existing `useSettingsActions` mutations into a state that gives `isPending` + `isSuccess` and wire them through.

If only one form is fixed before the demo: pick the Worker Settings cluster. If two: add the Workflow Builder stubs in #2, even just making the toast message match what the canvas does (or hiding Propose entirely until the AI route lands).

## Secondary findings worth noting

- **`zod` is installed, used in exactly one file.** The library is paid for and used at 4% capacity. A consolidation brief should mandate zod for any new form, with `useSignup`-style hook pattern (`safeParse` → state machine → in-flight disable → inline error). Cost is low and the consistency dividend is large.
- **`react-hook-form` is installed and unused.** Either commit to it across the wizard forms or remove it from `package.json`.
- **No `react-hot-toast` / `sonner` standardization for success feedback.** Workflow Builder uses sonner; HelpWidget uses inline `done` state; Worker settings use nothing; Hire Step 4 uses Radix Toast directly. Pick one toast library + write a `useFormSuccess(label)` helper.
- **Esc-to-close is provided by Radix Dialog wherever it's used.** The invite modal in #13 is the only modal that built its own overlay/portal — that's why Esc doesn't work there. Migrate to Radix.
- **Onboarding wizards preserve drafts via Zustand** (`use-onboarding-draft`, `use-hire-draft`). Good. The browser-back button doesn't break state. This is a real strength of the codebase to highlight.
- **The Genesis call has no dedicated modal**; it's the in-page Step 2 of the hire wizard (`Step2Listen.tsx`). If the brief was referring to a Genesis-mid-flow surface, it does not exist in the current codebase. Worth confirming with the conductor.
