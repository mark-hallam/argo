## 🔴 RED + root-cause synthesis (the new analysis this session)

### 1. Approvals counter — half regression, half by-design

The soak's "stays-0-on-reload" target conflates two things:

- **(a) REAL regression — the #2936 fix was clobbered post-merge.** #2936
  (`f584d1baa`, merged 2026-06-14) added `propagate_approval_to_rerun_session` so that
  approving probation-hold tool *T* — which re-runs the still-probationary teammate on a
  *fresh* session that re-emits a hold for *T* — nets exactly −1 for *T* (instead of
  −1 +N). On current HEAD the function was **gone**: `f584d1baa` is an ancestor of main,
  no later commit "touched" the file (default `git log` simplification hid it), yet
  HEAD's `routes_approvals_probation.rs` was **byte-identical to #2936's parent**. A
  concurrent PR branched from *before* #2936 and its merge resolution silently reverted
  the two files. **Restored this session** (exact re-apply of #2936's reviewed version +
  the `approve_converges_and_does_not_climb_on_reload` verifier).
- **(b) BY DESIGN — DEC-025 #2: "Probation: 24h, all actions approval-gated during it."**
  A brand-new teammate that keeps running during its first 24h *will* keep generating
  holds for genuinely-new actions; the queue growing reflects real held actions, which is
  the safety mechanism working. #2895 (2026-06-13) already fixed the *copy* to say so
  ("every run needs your OK; applies to that run only"). Forcing the counter to 0 here
  would *defeat* the probation gate — explicitly out of scope.

### 2. Approval-rate KPI resets to "—" on reload (real, polish)

`computeApprovalRate(items)` (`ApprovalsOpsDashboard.tsx:73`) counts only
`items.filter(i => i.decision != null)`, but resolved decisions drop out of the
`/approvals` list, so after a reload `decided.length === 0` → `null` → "—". The metric's
data source is the ephemeral pending queue, not the durable decision history. Fix queued
(`fix-approvals-rate-kpi-durable-from-audit`): derive it from `approval.granted` /
`approval.declined` audit rows, tenant-scoped.

### 3. `/landing` 500 — a stale-dev-server ghost (NOT product code)

Verified separately: `DemoVideoSlot.tsx` imported `Clock` until #2892 deleted it
*yesterday*; the soak's long-running dev server held the pre-#2892 module graph
("module factory deleted in an HMR update"). The current source has no `Clock` import,
its page test is 5/5 green, and the error is impossible in a production build (no HMR).
`/auth/signup` (the real funnel) is clean. No code fix — clean rebuild before any
deploy/recording.

## Process learning — the silent concurrent-merge clobber

The #2936 regression is the load-bearing process finding: **a merged, reviewed,
test-green fix was silently reverted by a later concurrent merge**, with `git log -- file`
showing nothing (history simplification hides a merge whose net effect vs first-parent is
"revert"). The disabled-CI / admin-merge-bypass v1 strategy means no post-merge gate
re-runs on the merged result, so the revert went unnoticed until this soak. The restored
verifier (`approve_converges_and_does_not_climb_on_reload`) will fail loudly under the
conductor pre-merge gate if it happens again — but the deeper guard is sequencing
concurrent merges that touch the same file, or a periodic `cargo test` sweep on main.
