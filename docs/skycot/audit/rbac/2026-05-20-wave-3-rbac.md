# Wave-3 Audit #4 — RBAC + 4-Role Enforcement Audit

**Date:** 2026-05-20
**Auditor:** Claude (Opus 4.7 1M, read-only sub-agent)
**Scope:** Web UI + gateway role enforcement on every sensitive action surface in the v1 demo path.
**Verdict (TL;DR):** **FAIL — the 4-role model is marketing copy, not enforcement.** A procurement security review would refuse it.

---

## 1 — Executive summary

SKYCOT advertises an enterprise-grade 4-role permission model (owner / admin / user / guest) on
`/pricing` and `/compare`, surfaces a polished invite-and-manage UX at `/settings/members` (#01b94775),
and ships an `argo-capability` Rust engine with correctly-modeled role defaults. The plumbing between
those three layers is **broken end-to-end**:

1. The web client (`web/lib/api/client.ts`) never sends `X-Argo-Role` or `X-Argo-Principal`.
2. The NextAuth JWT (`web/auth.config.ts`) never populates `session.role` or `session.permissions`
   — `useViewerPolicy` deliberately notes this and defaults every browser to "delegator".
3. The Rust gateway endpoints that DO check role read it from a **client-trusted HTTP header** —
   any caller can self-assign owner by sending `X-Argo-Role: owner`.
4. The role taxonomies are inconsistent across three layers (`owner/admin/user/guest` in the core
   engine + workflow routes, `delegator/operator/auditor/compliance-officer` in worker-settings +
   `useViewerPolicy`, and the `/settings/members` UI uses the first set).
5. The `/settings/members` invite UX is a pure UI stub — no `POST /api/v1/workspace/members`
   endpoint exists on the gateway.

The audit-feed PII redaction looks defensible (gateway always uses `RedactionPolicy::default` =
mask-all) but degrades the system into "everyone is a guest, redaction is unconditional" — i.e.
it works because nothing else does.

### Dimension 2: Redaction enforcement

- **Gateway side:** `routes_audit_feed.rs:91` and `routes_audit_detail.rs:45` use
  `RedactionPolicy::default()` (mask-all) for every caller, ignoring viewer role. This is
  safe-by-default but **never elevates** — even an owner can't see PII. The advertised "elevated
  view grant" workflow is not connected to the server policy.
- **Coverage gap (server):** the gateway redacts `verb` + `approver_name` only
  (`audit_row_json`). Other payload string fields (worker_name, channel, classification raw
  notes, etc.) are passed through unredacted. The brief said "fixed set of string fields";
  the set is narrow.
- **Web side:** `/audit/page.tsx:154` calls `useViewerPolicy()` + `redactAuditRow(row, policy)`
  on data already received from the gateway. Since `session.role` is never populated, every
  browser is "delegator" → all-mask. **Web redaction is cosmetic** — the gateway already
  returned masked text. If the gateway redaction ever weakens, the client is the last fence.
- **Elevated-view grants** (`use-elevated-view-grant.ts`): persisted in `localStorage` only.
  Any user can synthesize their own grant by writing `skycot.elevated-grants` in DevTools.
  Since the gateway data is already masked, the grant only flips local CSS classes — but
  the audit log will show no audit-the-audit row because no server is consulted.
- **AuditRedactedText** + **MemoryFactsCard** + **ActiveConversationsCard** + **ApprovalCard**
  call `useRedactionPolicy()` → POLICY_MASK_ALL on every session. Consistent.

### Dimension 3: Hire-flow permissions

- `/hire/page.tsx` and `/hire/step/[step]/page.tsx`: NO role check. Any authenticated user
  walks the wizard.
- `useHireWorker` → `POST /api/v1/workers`: NO check on either side. The gateway handler
  (`routes_workers_hire.rs`) trusts the bearer-auth done upstream and binds the new worker
  to the cwd-tenant. The "user vs guest" distinction is invisible here.
- Risk: a guest auditor who happens to have a valid bearer token can hire workers from
  a shared dev workspace.

### Dimension 4: View-level access

- `/settings/members` page is rendered for every signed-in user with no role check. A guest
  sees the full member list (Sam, Olivia, Diego, etc.) including all email addresses.
  Seed data, so not a real PII leak today, but the UX implies "you can see this page" to
  a role that should not.
- `/settings/data-export` is rendered for every signed-in user — guests, by the Members
  page's own role description, "cannot see billing or settings", yet the route does not
  enforce.
- `/settings` landing tile labelled "owner only" (workspace tile) marked `coming: true` —
  acceptable for now, but no underlying role gate either.
- `AppShell` global nav exposes every link to every signed-in user. There is no per-role
  nav. A guest sees `/hire`, `/workflows`, `/cohorts`, `/audit`, `/settings`, `/billing`.

### Dimension 5: Client-side vs server-side

For every action above:

- **Client-side check exists, server-side absent or trusted-header:** freeze, unfreeze, support
  tickets, workflows-edit, hard-delete worker. The client check is purely cosmetic; server
  enforces via a header the client doesn't send.
- **Client absent, server absent:** hire, pause, resume, archive, audit-feed, audit-detail,
  patch-channels/quiet/budget/autonomy, approvals decide/undo, billing.
- **Client absent, server present (correct):** none.

In every case where a server-side gate exists, it's a header-trust pattern, not a capability
derived from the bearer token. The bearer token (`session.gatewayToken`) carries no role
claim; the gateway has no way to derive role except by asking the client what role it wants.

## 3 — Three-taxonomy disagreement

| Taxonomy | Used by | Strings |
| --- | --- | --- |
| Core RBAC | `argo-capability`, `routes_workflows.rs`, Members UI | `owner` / `admin` / `user` / `guest` |
| Worker-settings danger | `routes_worker_settings_danger.rs`, `routes_worker_settings_helpers.rs:94` (`parse_role_header`) | `delegator` / `operator` / `auditor` / `compliance-officer` |
| Web viewer policy | `web/lib/redaction/types.ts:46`, `web/lib/hooks/use-viewer-policy.ts` | `delegator` / `operator` / `auditor` / `compliance-officer` |

The Settings/Members UI offers operator the four words "owner/admin/user/guest" but the
worker-settings backend wants "operator/delegator". Even if a future PR wires the bearer
token to carry a role claim, the role string from the JWT will not match what the
worker-settings handler is looking for unless mapped.

## 4 — Top 5 RBAC gaps to close before any procurement demo

Prioritized by enterprise-buyer impact. The order roughly matches Likelihood × Damage.

1. **APPROVALS HAVE NO RBAC.** `POST /api/v1/approvals/<id>/decide` and `/undo` accept any
   authenticated bearer with no role check. The marketed product is "human-in-the-loop AI
   workforce with approvals" — buyers will ask "who can approve?" and the answer is
   "anyone with a session". CVSS-style severity: HIGH-CRITICAL.
   `crates/argo-cli/src/handlers/gateway/routes_approvals_json.rs`.

2. **HIRE HAS NO RBAC + NO RATE LIMIT.** Any session can spawn workers. A compromised
   bearer token spawns a worker farm. `POST /api/v1/workers` in
   `routes_workers_hire.rs`. CRITICAL.

3. **WORKER-CONTROL HAS NO RBAC.** Pause / Resume / Archive / PATCH autonomy all open to
   anyone. Flipping a hospital-vertical worker from `conservative` to `aggressive` is one
   PATCH away with no gate. `routes_worker_settings_read.rs` + `routes_worker_settings_danger.rs`.
   CRITICAL.

4. **CLIENT-TRUSTED ROLE HEADER.** Every "gated" route (freeze, workflow-edit, support,
   delete-worker, cross-tenant audit) reads role from `X-Argo-Role` or
   `X-Argo-Audit-Cross-Tenant` — both client-supplied. Replace with role claims minted into
   the JWT by the signup/verify path, then parsed by the gateway from a trusted source
   (or derived from a server-side principal store keyed by `X-Argo-Principal`). The
   correct fix is: bearer token → DB lookup → role. Not a header.
   CRITICAL — this is the root-cause that makes every other "fix" lipstick.

5. **CROSS-TENANT AUDIT BYPASS.** `?as_tenant=<other>` honors `X-Argo-Audit-Cross-Tenant: 1`
   without ever checking the `audit.view.cross_tenant` capability the docstring claims
   should gate it. A malicious tenant in a shared-DB deployment reads any other tenant's
   audit log by curl with two headers. `routes_audit_feed_scope.rs:20`. CRITICAL for
   multi-tenant.

Honourable mentions (HIGH but not top-5):
- `/settings/members` invite is a UI stub — no backend.
- `/audit/export` UI advertises evidence bundles; no gateway endpoint.
- Three role taxonomies (owner/admin/user/guest vs operator/delegator/auditor/compliance-officer).
- AppShell shows every link to every role.

1. **`mission-enterprise-bearer-token-role-claim`** — populate `session.role` from a
   server-side `workspace_member` table; mint role into JWT; remove `X-Argo-Role` header
   trust on the gateway side.
2. **`mission-enterprise-approvals-rbac`** — gate `POST /api/v1/approvals/<id>/decide`
   behind the `Approval` capability and a per-policy minimum-role check.
3. **`mission-enterprise-hire-rbac`** — gate `POST /api/v1/workers` behind `WorkerHire`
   (new capability) granted only to owner + admin.
4. **`mission-enterprise-worker-control-rbac`** — gate pause/resume/archive/PATCH-autonomy.
5. **`mission-enterprise-cross-tenant-audit-fence`** — replace the header-trust pattern
   in `routes_audit_feed_scope.rs` with a real capability check.
6. **`mission-enterprise-members-crud-api`** — actually ship `POST/DELETE
   /api/v1/workspace/members` so the invite modal does something.

   string payload fields, and resolve `RedactionPolicy` from the principal's role.

## 6 — Verdict: would the 4-role model survive a procurement security review?

**No.**

A standard SOC2/ISO27001/HIPAA procurement question set ("show us how role-based access
controls are enforced for sensitive operations; demonstrate that a 'guest' cannot perform
admin actions") would fail at the first probe.

A live demo: log in as the "guest" seed user (Naomi, `naomi@auditor.gov`); open
`/workers/[any-id]`; click Freeze; observe success. The guest just froze a worker. End of
demo. The reviewer rejects.

**To survive a procurement review, items 1–5 in §4 must close.** Items 1, 4, 5 are the
true blockers — items 2, 3 are remediated automatically once item 4 unwires
header-trust and replaces it with JWT-claim-derived role.

The optimistic read: the *foundation* is right (`argo-capability` is a sound engine,
default roles are correctly modelled). What's missing is the wiring between bearer-token
→ principal-role → gateway-cap-check. That's ~3 briefs of work, not a re-architecture.
But until it lands, every "enterprise RBAC" claim on the marketing site is unsubstantiated.
