- **Audit date**: 2026-05-25 (Melbourne local)
- **Auditor**: e2e UX journey agent (read-only)
- **Scope**: v1.0 demo MP4 runbook Scene 1 (`/workers` + `/workers/{id}` C2-personality detail) and Scene 2 (Schedules/Responsibilities tab → Run now → audit row drill-in)
- **Method**: SPA driven via Claude Preview MCP against the live gateway on port 7400; cross-referenced against locked-design memories + the personas in `web/lib/sample-personas.ts`
- **State of the world**: swarm PAUSED per `CLAUDE.md`; main is at d7c550e34; gateway alive (`/health` returns 200, schema_version 81); 1 worker ("Maya · marketing-intern") seeded in the gateway

## TL;DR

The v1.0 demo MP4 **cannot be recorded against today's build for Scenes 1 and 2** without three fixes. Six P0 demo-blockers were found. The good news: the C2-personality design memory IS implemented and looks correct when it renders (see Mariah path). The bad news: the gateway and SPA are out of sync on three contract surfaces (charter shape, audit drill-in, workers list shape) so the live demo path crashes; the Responsibilities tab Scene 2 narrates simply does not exist; and the persona seeded for demo recording is not one the runbook names.

- **6 P0** (demo-blockers) · **4 P1** (visible) · **3 P2** (polish)
- Worst blocker: `WhatSheDoesCard` crashes the entire worker-detail page to a 500 error boundary when the gateway returns the real `charter` object — Scene 1 click-through `/team` → worker is unrecordable.
- Second worst: the Responsibilities tab Scene 2 hinges on has no `page.tsx` and is not wired into `WORKER_TAB_IDS`. There is no "Run now" UI affordance anywhere in the worker detail. Scene 2 cannot be recorded as scripted.
- Third worst: audit `/audit/action/<id>` drill-in returns "Action not found" for IDs the list endpoint just returned. Scene 6's provenance click is broken (out of this audit's scope but discovered in passing).

## Headline blockers

1. **[P0] Worker-detail Overview crashes to 500 on real gateway data.** `WhatSheDoesCard` renders the `charter` field directly inside `<p>`, but the gateway now returns `charter` as `{last_edited_at, last_edited_by, text, version}`. Scene 1 click-through from `/team` to Maya is unrecordable.
2. **[P0] Responsibilities tab does not exist as a page or as a tab.** Scene 2 cannot be navigated to through the UI. `/workers/[workerId]/responsibilities/` contains only `new/page.tsx`. `WORKER_TAB_IDS` omits both `responsibilities` and `evals`.
3. **[P0] No "Run now" button anywhere in the worker detail.** Scene 2's centerpiece interaction has no UI affordance.
4. **[P0] Gateway has 1 worker named "Maya · marketing-intern", not the 5 the runbook names.** No real seed data for Mariah / Peta / Priya / Jamal / Nori. The DEMO_SEED CLI list and the SPA SAMPLE_TEAM list disagree.
5. **[P0] Audit drill-in 404s on rows that the timeline just rendered.** `/audit/action/<id>` returns `{"error":"not found"}` for the same ids `/api/v1/audit` returned 2 seconds earlier. Confirmed both via the SPA and via curl directly.
6. **[P0] Audit rows have `worker.name = "unknown"` and the verb column shows `hipaa_compliance_check` — a healthcare action on a marketing-intern tenant.** Scene 2's "audit row lands within 5s with real worker_id" cannot pass when the worker_id is empty.

## All findings

### Scene 1 — workers roster + worker-card → detail click-through

#### F1 [P0] — Worker-detail Overview crashes to 500 on real-gateway `charter` object

The gateway endpoint `GET /api/v1/workers/<id>/overview` returns `charter` as `{last_edited_at, last_edited_by, text, version}` (a versioned charter envelope). `web/components/skycot/worker/WhatSheDoesCard.tsx:156` renders `{charter}` directly as a child of `<p>`. React throws `Objects are not valid as a React child (found: object with keys {last_edited_at, last_edited_by, text, version})` which the worker `error.tsx` catches and renders as the full-page 500.

- Reproduction:
  - `curl -b cookies http://127.0.0.1:7400/api/v1/workers/<gateway-worker-id>/overview` — confirm `charter` is an object.
  - Open `/workers/<gateway-worker-id>/overview` in the SPA.
  - Observe the page renders the hero + tabs, then the body crashes to the 500 error shell with the "Try again" + "Back to team" buttons.
- File path: `web/components/skycot/worker/WhatSheDoesCard.tsx:156`, type declaration at `web/lib/api/worker-overview.ts:61` (`charter: string`)
- Suggested fix: Update the SPA `OverviewResponse` schema to `charter: { text: string; version: number; last_edited_at: string; last_edited_by: string }` and render `{charter.text}` — there's already a `version`-aware editor scaffold suggesting this was meant to land.

#### F2 [P0] — Gateway demo data is "Maya · marketing-intern", not the runbook's 5 workers

The runbook calls out **Mariah / Peta / Priya / Jamal / Nori** as the 5 trading-card workers on `/workers`. The gateway today seeds **one** worker named "Maya" with vertical `marketing-intern`. None of the 5 personas the runbook narrates exist in the gateway. Per the `feedback_no_theater_in_demo` memory the demo MUST be REAL not mocks — the seed CLI rewrite (Option B) was operator-locked but the seed isn't running for this dev profile.

- Reproduction:
  - `curl -b cookies http://127.0.0.1:7400/api/v1/team` — observe `total_count: 1` with name "Maya".
- Suggested fix: Run `argo demo seed --tenant <demo>` (or the equivalent seed CLI) before recording. The persona definitions for Mariah/Peta/Priya/Jamal/Nori already live in `web/lib/sample-personas.ts` (`DEMO_SEED_PERSONAS`), so the seed should reuse those.

#### F3 [P0] — SPA fallback persona list does not match the runbook (drops Peta, includes Sam + Rio)

The SPA-only fallback `SAMPLE_TEAM` (used when the gateway returns 404) draws from `SAMPLE_PERSONA_IDS = [Mariah, Priya, Jamal, Nori, Sam, Rio]`. Meanwhile `DEMO_SEED_PERSONAS = [Mariah, Peta, Priya, Jamal, Nori]`. These two lists are authored in the SAME FILE (`web/lib/sample-personas.ts:171-188`) and disagree. If anything pushes the demo onto the mock fallback path, the runbook scene-1 names are wrong (no Peta, plus two extra personas).

- File path: `web/lib/sample-personas.ts:181-188`
- Suggested fix: Align `SAMPLE_PERSONA_IDS` to match `DEMO_SEED_PERSONAS` exactly: `[MARIAH.id, PETA.id, PRIYA.id, JAMAL.id, NORI.id]`. Sam + Rio remain defined for tests but are not in the demo list.

#### F4 [P0] — `TeammateCard` has no Peta entry in `TRAITS_BY_NAME` or `LEVEL_BY_NAME`

Even if Peta is added to the fixture list, her trading card will render with a hash-derived level and empty trait list, breaking the C2 holographic-showcase brand consistency. Memory `project_pm_cohorts_peta_patrick` describes Peta as a Project Coordinator L2 with specific personality traits.

- File path: `web/components/skycot/TeammateCard.tsx:51-67`
- Suggested fix: Add `Peta: ["Organised", "Quietly persistent", "Calm in chaos"]` (or similar) to `TRAITS_BY_NAME` and `Peta: 4` (or matching Project Coordinator L2) to `LEVEL_BY_NAME`. Same fix needed in `WorkerPersonalityCard.tsx:35-95` (the four-card personality detail map).

#### F5 [P0] — `/workers` is a stub that auto-redirects to `/team`

The nav-bar entry the runbook references (`/workers`) is implemented in `web/app/(app)/workers/page.tsx` as a router-replace to `/team` whenever workers exist (the "shared-empty-state" pattern described in the file comment). The runbook narrates `/workers` as if it is the canonical surface. This creates a visible URL flicker in the demo recording: the nav highlights "Workers" but the URL ends up `/team`.

- File path: `web/app/(app)/workers/page.tsx:1-46`
- Suggested fix: Either (a) script the demo to navigate to `/team` directly and update the runbook to match, (b) collapse the `/workers` redirect so the surface lives at `/workers` and `/team` 301s to it, or (c) make the breadcrumb on worker-detail say "Workers" (currently "Team") so the entire surface is consistent. The internal contradiction — nav says Workers, breadcrumb says Team, URL says Team — is the bug.

#### F6 [P0] — `TeammateCard.tsx` is 582 LOC (exceeds the project's 500-LOC budget)

CI invariant per `CLAUDE.md` ("No file > 500 LOC") is currently violated by `TeammateCard.tsx` — 582 lines. Not a demo-blocker on its own but it means any change to add Peta or fix the F4 trait map will trip CI.

- File path: `web/components/skycot/TeammateCard.tsx`
- Suggested fix: Extract the `TRAITS_BY_NAME` / `LEVEL_BY_NAME` maps + the `<style jsx>` block (likely ~150 LOC) to sibling files (`TeammateCardTraits.ts`, `TeammateCardStyles.tsx`).

#### F7 [P1] — Team-page hero internally contradicts the worker count

When the gateway has 1 worker (Maya in `idle` status), the team page renders the hero as **"Your first teammate is working"** with KPI **"0 working right now"** and **"187 actions this week"** + **"saving you ~12 hours"**. "Working" in the hero and "0 working" in the KPI strip directly contradict each other on the same screen. The 187 / 12 numbers are `workers.length * 187` and `workers.length * 12` — dressing math that doesn't reflect reality.

- File path: `web/app/(app)/team/page.tsx` (the `weeklyActions = workers.length * 187` block)
- Suggested fix: Either drop the hero copy when `working === 0`, or make the hero copy reactive: "Your team is ready" when idle, "Your team is working" only when at least one worker is in `working` status.

#### F8 [P1] — Worker-detail page title is the raw UUID

`document.title` on `/workers/<id>/overview` is `"018f67d0-0000-7000-8000-000000000001 · Overview"` (and similarly the lowercase `responsibilities` segment when navigating to that route). The Next.js metadata template is using the URL segment as the title fallback instead of the worker name. The camera will capture this in browser tab + cmd-Tab views.

- File path: `web/app/(app)/workers/[workerId]/layout.tsx` (no `generateMetadata` defined — falls back to the route segment)
- Suggested fix: Add `generateMetadata` to the layout that reads the worker name (server-side) and returns `{ title: \`${name} · Overview\` }`.

### Scene 2 — Schedules/Responsibilities tab + Run now + audit row

#### F9 [P0] — Responsibilities tab is missing from the worker-detail tab list

`WORKER_TAB_IDS` at `web/components/skycot/WorkerTabs.tsx:19-27` contains only `[overview, activity, memory, skills, trust, escalation, settings]`. The runbook narrates 9 tabs (the above 7 + `evals` + `responsibilities`). Neither extra tab is wired. Scene 2 cannot start: the camera has no clickable tab to take it to "Schedules".

- File path: `web/components/skycot/WorkerTabs.tsx:19-39`
- Suggested fix: Add `"responsibilities"` (label "Schedules" per the operator-locked UI vocab in memory `project_vocabulary_duty_vs_schedule`) and `"evals"` to both the IDs array and the labels map.

#### F10 [P0] — `/workers/[workerId]/responsibilities/page.tsx` does not exist

The `responsibilities/` directory only contains `new/page.tsx` (the create form). The tab page itself was never authored. Even if F9 is fixed, the tab click would hit the catch-all `[tab]/page.tsx` and land in `notFound()`.

- File path: `web/app/(app)/workers/[workerId]/responsibilities/` (page.tsx absent)
- Suggested fix: Author a `responsibilities/page.tsx` that uses `useWorkerOverview(workerId)`'s `duties` array and renders cron-shaped rows. The data shape is already returned by the gateway (the `duties: []` field in `/workers/<id>/overview`).

#### F11 [P0] — No "Run now" button anywhere in the worker UI

`rg "Run now|RunNow|run_now"` across `web/components/skycot/worker` returns zero matches. The only related API surface is `lib/api/orchestration.ts` (run-run cancel/reset, not duty trigger). Scene 2's "Click Run now on listing_health_check" interaction has no UI implementation.

- Suggested fix: Add a per-duty "Run now" button on the (yet-to-author) Responsibilities page that POSTs to a duty-trigger gateway endpoint and writes an audit row. The brief needs both the gateway endpoint + the SPA control.

#### F12 [P0] — Audit list ↔ drill-in disagreement: `/audit/action/<id>` returns "Action not found" for IDs the list just returned

`/api/v1/audit?limit=5` returned 3 rows. Clicking the first row in the SPA navigates to `/audit/action/019e5dbaec037fa2819eab3f27f3f41e`. The SPA fetches `/api/v1/audit/action/019e5dbaec037fa2819eab3f27f3f41e` which returns `{"error":"not found"}`. The SPA then renders "Action not found · The action may have been redacted, hard-deleted by a retention policy, or the id is incorrect." This is out of Scene 1/2 strict scope but Scene 2's "audit row lands within 5s" hinges on the drill-in being real per the function-vs-dressing rule.

- Reproduction:
  - `curl -b cookies http://127.0.0.1:7400/api/v1/audit?limit=5` — copy an id
  - `curl -b cookies http://127.0.0.1:7400/api/v1/audit/action/<id>` — observe 404
- Suggested fix: Investigate the gateway route — the list and single endpoints likely query different tables / use different tenant scoping. Confirm both endpoints read from the same audit-log source.

#### F13 [P0] — Audit row attribution is "unknown" worker with no id

Every existing audit row in the demo tenant has `worker: {id: "", name: "unknown"}`. The list endpoint returns this directly. The runbook says "Verify the audit row's payload is REAL (real worker_id, real tenant_id, real action description — not a fixture)" — today every audit row fails that check on `worker_id` and `name`. Also note the rows all have `action_type: "hipaa_compliance_check"` — a healthcare compliance action on a marketing-intern tenant (clearly a stray test fixture row).

- Suggested fix: Re-seed the audit table from the seed CLI (per `feedback_no_theater_in_demo` Option B) so every row has a real worker reference and a real action description.

### Cross-cutting

#### F14 [P1] — Two env-var naming mismatches in `.claude/launch.json` prevent the demo data path from loading

`.claude/launch.json` sets `NEXT_PUBLIC_GATEWAY_AUTH_BYPASS=1` and `NEXT_PUBLIC_ARGO_DEMO_MODE=1`. But:
- `web/lib/skycot/demo-mode.ts:20` reads `NEXT_PUBLIC_SKYCOT_DEMO_MODE` (different name) — so `isDemoMode()` returns `false` in the dev profile, and `fetchTeam` does NOT fall back to `SAMPLE_TEAM` on a gateway 404. The team page silently renders the empty state.
- `web/lib/api/team.ts:42` reads `NEXT_PUBLIC_ARGO_GATEWAY_AUTH_BYPASS` (matches the var in middleware.ts) — but `.claude/launch.json` writes `NEXT_PUBLIC_GATEWAY_AUTH_BYPASS` (missing the `ARGO_` prefix). So the auth-bypass branch in the lib never fires.

Net effect: a fresh `pnpm dev` from this config gives the operator the empty-state CTA grid (Hire your first teammate) instead of the demo team. Anyone resuming this audit on a new machine will hit the same problem.

- File path: `.claude/launch.json:6-13`
- Suggested fix: Replace the two env vars with `NEXT_PUBLIC_SKYCOT_DEMO_MODE=1` and `NEXT_PUBLIC_ARGO_GATEWAY_AUTH_BYPASS=1`. Or update the lib reader to honor both names with a deprecation note.

#### F15 [P1] — Worker-detail breadcrumb says "Team" while left-nav highlights "Workers"

On `/workers/<id>/overview` the page breadcrumb reads "Team › Mariah" while the left nav highlights "Workers". This is a direct consequence of F5 (the `/workers` → `/team` redirect ambiguity) but is independently jarring on camera.

- File path: `web/app/(app)/workers/[workerId]/WorkerLayoutShell.tsx:100`
- Suggested fix: Choose one. If "Workers" is the camera-visible nav, the breadcrumb should also say "Workers".

#### F16 [P1] — Demo-mint cookie does not survive navigation cycles via `location.assign`

When driving the SPA through `mcp__Claude_Preview__preview_eval`, the `__Host-session` cookie set by `/api/auth/demo-mint` is dropped intermittently between hard navigations, causing the middleware to bounce subsequent requests to `/landing`. The cookie comes back when the SPA's `/api/auth/session` is hit and re-mints. Probably an `HttpOnly` + `Secure` + preview-eval origin interaction.

This affects the rehearsal-script reliability — if the camera operator does a hard refresh mid-take they may bounce to /landing. For the operator, recording in a fresh real browser (not the eval-driven preview) should be fine, but the brittleness is real.

- Suggested fix: Verify the demo recording uses a real Chrome profile (per memory `project_v1_demo_mp4_ship_gate` — "fresh Chrome profile"). Don't try to drive demo rehearsals through the Preview MCP.

#### F17 [P2] — Audit row "verb" column shows the raw machine action key

Each row's verb cell shows `hipaa_compliance_check` (the action_type string) rather than a verb-style human label like "Ran HIPAA compliance check". Scene 6 narrates the camera reading the audit verbs aloud — these should be human-readable.

- File path: presumably `web/components/skycot/audit/ActivityRow.tsx` or similar
- Suggested fix: Build a `verbForAction(actionType)` mapping or accept a `verb` field from the gateway (which is already there but contains the same machine key).

#### F18 [P2] — Audit row avatar shows "UN" (Unknown) instead of worker initial

Tied to F13 (worker reference is empty). Once the audit rows have real worker references, the avatar shows the correct initial. Until then the demo cannot drill into a real worker from the audit timeline.

#### F19 [P2] — Browser `document.title` template format inconsistent

`/workers/<id>/responsibilities` returns title `"018f67d0-... · responsibilities"` — lowercase tab segment leaked into the title (no template). `/workers/<id>/overview` returns `"018f67d0-... · Overview"` — capitalized. Tied to F8.
