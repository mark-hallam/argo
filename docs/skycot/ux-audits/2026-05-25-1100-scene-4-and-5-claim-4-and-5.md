### F1 [P0] — `/workflows` ships "WORKFLOWS · MOCK" eyebrow pill on screen

The catalog page renders a brand-eyebrow pill that flips between `WORKFLOWS · LIVE` and `WORKFLOWS · MOCK` based on whether the `useWorkflows()` query lands a gateway response. With the current gateway state (empty per-vertical workflow lists) the page falls through to `SAMPLE_WORKFLOW_SUMMARIES` from `lib/sample-workflows.ts` and the pill shows **MOCK**. The pill is up-top-and-left, large, in the brand purple accent dot — it is structurally a piece of the demo-recording surface that the camera cannot avoid.

This violates the operator-locked "no theatre in the demo" rule for Scene 5: this page IS the on-camera narrated surface for Claim 5; the operator's voiceover talks about "real-world execution" while the page literally labels itself MOCK.

- Reproduction:
  - `open http://localhost:3000/workflows` (or click Workflows in the sidebar)
  - Read the eyebrow row immediately above the H1 — it says `· MOCK`
  - Verify via DOM: `document.querySelector('[data-testid="workflows-source-pill"]').textContent` returns `"WORKFLOWS · MOCK"`

- File path: `web/app/(app)/workflows/page.tsx:68` (the literal `{isLive ? "LIVE" : "MOCK"}` ternary in the JSX)
- Driving condition: `web/lib/api/workflows.ts:155` (returns `source: "mock-offline"` when buckets are empty)
- Suggested fix: either seed real per-vertical workflow rows so `source` becomes `"gateway"` before recording, OR drop the MOCK suffix entirely (e.g. `WORKFLOWS · v0.1` regardless of source) — the source-pill belongs in dev tooling, not on the demo surface.

### F6 [P1] — Gateway `OPTIONS /skills` returns 404; the SPA browser-fetch fails (Cross-Origin Resource Sharing preflight)

CORS (Cross-Origin Resource Sharing — browser rule that controls when a webpage on one origin can talk to a server on another origin) preflight fails on the un-prefixed `/skills` endpoint:

```
$ curl -X OPTIONS http://127.0.0.1:7400/skills → 404
$ curl http://127.0.0.1:7400/skills          → 200 (empty envelope)
$ curl -X OPTIONS http://127.0.0.1:7400/api/v1/skills → 204
```

The SPA hook `useSkills()` (`web/lib/api/skills.ts:142`) calls `apiGet("/skills")` which resolves to `http://127.0.0.1:7400/skills` (NOT `/api/v1/skills`). The browser blocks the call at preflight, the hook errors, and the page falls through to the 6-card seed list. So the page *appears* fine but is structurally talking to nothing — the source-pill on `/workflows` is also flipped to MOCK for the same reason (separate but related broken-endpoint pattern).

This is **also** the reason cross-tenant isolation can't be tested on `/skills`: a fresh install would never propagate via the broken API anyway.

- Reproduction:
  - `curl -X OPTIONS -H "Origin: http://localhost:3000" http://127.0.0.1:7400/skills` → 404
  - Open dev-tools Network panel on `/skills` → fail row for `127.0.0.1:7400/skills`

- File path: routing for `OPTIONS /skills` is missing in `crates/argo-cli/src/handlers/gateway/` — the canonical prefixed route at `/api/v1/skills` returns 404 to GET as well (different bug); the SPA is hitting whichever the apiGet base URL resolves to.
- Suggested fix: either (a) re-point the SPA's `apiGet("/skills")` calls at `apiGet("/api/v1/skills")` after adding that gateway route, or (b) add the OPTIONS preflight handler for the un-prefixed `/skills` route. Either way, run a smoke `curl -X OPTIONS` against every endpoint the SPA actually calls.

### F8 [P1] — `/workflows/build` returns 404; no top-level "build a workflow from scratch" entry-point

The scope brief asks: "**Workflows builder** at `/workflows/build` — does it let an operator compose a multi-step workflow?" Answer: that URL doesn't resolve.

```
$ curl -I http://localhost:3000/workflows/build → 404
$ curl -I http://localhost:3000/workflows/sales/qualify_lead/build → 200
```

The builder lives at `/workflows/[verticalId]/[name]/build` — you can only EDIT an existing workflow, never compose a new one from a blank canvas. The `Propose new` button on `/workflows` opens a modal that proposes a workflow in plain English (`WorkflowProposeModal`); it does not lead to a blank builder canvas.

- File path: directory `web/app/(app)/workflows/` has no `build/` subroute; only `[verticalId]/[name]/build/`
- Suggested fix: either ship a thin `/workflows/build/page.tsx` that asks "which vertical?" then routes into the builder, or drop the `/workflows/build` reference from the scope brief and verify the builder via an existing workflow's edit path.

### F9 [P1] — Builder uses `SAMPLE_WORKFLOW_SPECS` as a hard-coded fallback path (`SEED_WORKFLOWS`)

The builder canvas (`web/app/(app)/workflows/[verticalId]/[name]/build/`) imports `SEED_WORKFLOWS` from `seed-workflows.ts` and uses it as the sub-workflow picker source. `web/app/(app)/workflows/[verticalId]/[name]/build/SubWorkflowPicker.tsx:5` reads:

```
import { SEED_WORKFLOWS } from "./seed-workflows";
…
return Object.entries(SEED_WORKFLOWS) …
```

Combined with F1: the operator opening the builder during Scene 5 and dragging a sub-workflow node into the canvas will get a sub-workflow picker populated entirely from a local TypeScript fixture, never the gateway. The scope brief explicitly asks "Does the `/workflows/build` canvas hit the real gateway (not a `SEED_WORKFLOWS` static fixture)?" — answer for the sub-workflow picker is NO. Other surfaces of the builder (the step-config inspector, the AI proposal stream) do route through real endpoints; this is a single-component leak.

- File path: `web/app/(app)/workflows/[verticalId]/[name]/build/SubWorkflowPicker.tsx:24`
- Suggested fix: wire `SubWorkflowPicker` to `useWorkflows()` and treat `SEED_WORKFLOWS` as the empty-state-only fallback (gate behind `data?.workflows.length === 0`).

### F10 [P2] — "BY RIO / BY SAM" rendering should also be hardened by a roster-check unit test

Even if F4 ships a rename, the file `web/lib/sample-workflows.ts` has no compile-time guarantee that `lastEditor` is from the canon roster. A roster-mismatch lint will eventually slip back. Suggest a unit test asserting every `lastEditor` value in `SAMPLE_WORKFLOW_SUMMARIES` is `∈ {Mariah, Maya, Peta, Priya, Jamal, Nori, SKYCOT, system}` so a future drive-by edit doesn't reintroduce the bug.

- File path: would live at `web/lib/sample-workflows.test.ts`
- Suggested fix: 8-line test, no runtime impact.

### F11 [P2] — Skills page hero count says "6 skills · 0 shown" during empty search, not "0 results"

Cosmetic. When the operator types a query with no matches, the count pill at the top reads `6 skills · 0 shown`. The body below reads `No skills match "competitor pricing scrape"`. The two phrasings are redundant and a touch jarring. Lower-case "shown" → "match" or drop the second clause entirely when filtered.length === 0.

- File path: `web/app/(app)/skills/page.tsx` (count-pill JSX, around the eyebrow row)
- Suggested fix: when `filtered.length === 0`, show `0 of 6` instead of `6 skills · 0 shown` to align with the empty-state body language.
