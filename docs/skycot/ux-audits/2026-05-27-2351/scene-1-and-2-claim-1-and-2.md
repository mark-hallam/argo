# Scene 1 + Scene 2 e2e UX audit — Claim 1 (Teammate, not tool) + Claim 2 (Delegation is the unit)

**Audit time**: 2026-05-27 23:51 Melbourne (local) — equivalent UTC 2026-05-27T13:51Z onwards.
**Agent**: e2e-ux-journey-test-agent (read-only).
**Gateway**: `http://127.0.0.1:7400`, schema v83 FRESH, uptime ~9.5 hours.
**SPA**: Next.js / Turbopack on `http://localhost:3000` (port 3000 had no demo env vars; the audit used the preview launch profile `web` which booted with `NEXT_PUBLIC_ARGO_GATEWAY_AUTH_BYPASS=1 NEXT_PUBLIC_SKYCOT_DEMO_MODE=1 NEXT_PUBLIC_SKYCOT_DEMO_LIVE=1` on port 61039).
**Scope**: only Scenes 1 + 2 of `docs/skycot/demos/v1-mission-mvp-runbook.md`.
**Read-only**: no source files edited; gateway state untouched.

## TL;DR

15 findings (5× P0 / 6× P1 / 3× P2 / 1× P3). The biggest blocker is structural: **with the current demo launch profile, the entire `/team` + `/workers/{id}` surface short-circuits to hardcoded SAMPLE data and never asks the gateway**. That makes Scene 1's "stop gateway, restart it — same 5 teammates reappear with stable worker_ids" UNRECORDABLE as scripted (the page would render identically with the gateway turned off — proving nothing about persistence). Scene 2 has its own structural blocker: the Schedules tab renders the duty list correctly, but **there is no "Run now" affordance anywhere**, and even if it existed, the gateway has emitted zero `worker_duty.fired` audit rows so `/audit` filter would stay empty. The audit drill-in API the runbook depends on returns 404 for every action id the list endpoint returns. The function-side promise of Claims 1 + 2 is currently undemonstrable; the camera would record theatre.

## Findings, in order

### F01 [P0] — `/team` and `/workers` never call the gateway under the demo launch profile

`web/lib/api/team.ts:85-97` returns `SAMPLE_TEAM` immediately when `isAuthBypassed()` is true (i.e. `NEXT_PUBLIC_ARGO_GATEWAY_AUTH_BYPASS=1` is set, which the launch config DOES set). The check does NOT consult `isDemoLive()`. By contrast, `web/lib/api/audit-detail.ts:95` does the right thing: `if (isAuthBypassed() && !isDemoLive())`.

Evidence of the divergence between the rendered page and gateway state:
- Gateway `/api/v1/team` returns 5 workers with IDs `019e6785-928a-…` through `019e6785-928f-…` (real UUIDv7s, generated by the seed CLI).
- Rendered `/team` page snapshot shows the same 5 names (Mariah / Peta / Priya / Jamal / Nori) but with IDs `018f67d0-0000-7000-8000-000000000001..7` (hardcoded sample personas, `web/lib/sample-personas.ts:56,73,90,106,123`).
- The card's profile-link selector is `TeammateCard.tsx:122` → `/workers/${worker.id}/overview` — clicking through opens the SAMPLE id, not the gateway id.

Why P0 for the POC demo: Scene 1's load-bearing claim is "stop the gateway, restart, the workers reappear because they are real persisted identities." With this short-circuit, the page renders identically whether the gateway is up, down, or seeded with completely different workers. Scene 1 proves nothing about Claim 1; it proves the SPA has a hardcoded fixture.

Reproduction:
1. `curl -s http://127.0.0.1:7400/api/v1/team | jq '.workers[].id'` → returns 5 `019e6785-…` UUIDs.
2. Load `/team` on the demo-launch SPA.
3. Inspect a worker card's `aria-label` / link href — IDs are `018f67d0-0000-…`, not the gateway's.
4. Stop the gateway, reload `/team` — the page still renders the same 5 cards (proving the gateway wasn't consulted).

File:line refs:
- `web/lib/api/team.ts:47-52` (`isAuthBypassed()` definition)
- `web/lib/api/team.ts:85-97` (the unconditional `SAMPLE_TEAM` return)
- `web/lib/sample-personas.ts:56,73,90,106,123` (hardcoded persona IDs)

Suggested fix: pattern-match `audit-detail.ts:95` and add `&& !isDemoLive()` to the auth-bypass branch in `fetchTeam`; do the same in `fetchWorkerOverview`, `fetchSkills`, `fetchWorkflows`. Add the canonical seed step to the recording pre-flight checklist.

### F04 [P0] — Audit detail endpoint `GET /api/v1/audit/<id>` returns 404 for every list item

`curl -s "http://127.0.0.1:7400/api/v1/audit?range=7d" | jq -r '.items[0].id'` returns e.g. `019e69bae0d37b33aeff82fb8a9df4a8`. Then `curl -i "http://127.0.0.1:7400/api/v1/audit/019e69bae0d37b33aeff82fb8a9df4a8"` returns:

```
HTTP/1.1 404 Not Found
{"error":{"code":"not_found","message":"audit row not found"}}
```

I confirmed this against the first and last items in the 50-row list — both 404. Also tried `/api/v1/audit/action/<id>`, `/api/v1/audit/actions/<id>`, `/api/v1/audit/events/<id>` — all return 404 with hint `"see /api/v1/audit or /api/v1/audit/events"` (and `/api/v1/audit/events` itself returns 404).

The SPA's `audit-detail.ts:103` constructs the path `/api/v1/audit/${encodeURIComponent(actionId)}` — the same path that 404s. Because `audit-detail.ts:106-109` catches the 404 and throws `AuditDetailNotFoundError`, the in-shell 404 page renders instead of the provenance card.

Why P0: not in Scene 2 directly, but Scene 2's narration says "Cut to /audit. Filter by `kind = worker_duty.fired`. The row appears with `duty_id`, `session_id`, and `tenant_id` payload intact." (runbook L165-168). Drilling into a row is essential to show that payload. With this 404, the camera lands on a 404 page in `audit-detail.ts:88-109`. Also breaks Scene 6 (audit drill-in is the headline beat).

Reproduction:
1. `ID=$(curl -fsS http://127.0.0.1:7400/api/v1/audit?range=7d | jq -r '.items[0].id')`
2. `curl -i "http://127.0.0.1:7400/api/v1/audit/$ID"` → 404.
3. The same id is present in the list payload above.

File:line refs:
- gateway-side bug — owner is the `argo-gateway` audit-detail handler. (Not in `web/`; suggest the parent agent surface this to the gateway team.)
- `web/lib/api/audit-detail.ts:103-109` (consumer that 404s on demo data)

Suggested fix: gateway must register `GET /api/v1/audit/{id}` as a real handler that fetches the row by id from the audit store. The list endpoint already returns these ids — the detail endpoint should be able to fetch by the same identifier.
