# Vulnerability Management Workflow

**Owner:** security@skycot.com (P0 / P1) · eng-leads@skycot.com (P2 / P3)
**Scope:** Rust + transitive crate dependencies + first-party
in-repo code. Container-image CVE scanning, web CVEs covered by
Dependabot, and secret scanning live in separate workflows.
**Disclosure:** see `docs/skycot/SECURITY.md` §Reporting.

This document is the load-bearing process artefact for the
SOC2-CC7.1 / ISO 27001 A.12.6.1 control: "Technical vulnerabilities
shall be identified, evaluated, and patched in a documented and
auditable way." Operators following it produce the evidence trail
auditors ask for.

---

## 1. Severity taxonomy

Skycot uses a four-tier severity scheme aligned with CVSS v3.1
score bands. Each tier has a default named owner and a triage SLA
the on-call operator commits to from the moment the advisory is
acknowledged.

| Tier | Label    | CVSS v3.1 | Owner             | Triage SLA |
| ---- | -------- | --------- | ----------------- | ---------- |
| P0   | Critical | 9.0–10.0  | security@skycot   | **4 h**    |
| P1   | High     | 7.0–8.9   | security@skycot   | **24 h**   |
| P2   | Medium   | 4.0–6.9   | eng-leads@skycot  | **7 d**    |
| P3   | Low      | 0.1–3.9   | eng-leads@skycot  | **30 d**   |

A score-less advisory (RustSec uses qualitative severity for some
older advisories) maps to the conservative tier: any advisory
marked `critical`, `high`, `medium`, `low` by RustSec uses those
labels directly. Anything tagged "unsound" or "memory-corruption"
is auto-promoted to P1 regardless of declared severity. Operators
may override per-org by editing the override table in
`argo.toml § [security.severity_override]` (not in v1).

### What "triage SLA" means

Triage SLA is the window between **advisory acknowledged** (a
human marked the row read) and one of:

1. **Mitigation merged** — version bumped, code patched, or
   workaround landed on `main`.
2. **Mitigation noted** — written explanation of why the advisory
   does not apply (false positive, unreachable code path, mitigated
   by an existing config). Status flips to `mitigated`.
3. **Risk accepted** — short statement + named accept-er. Status
   flips to `wontfix`. Requires a CTO-level sign-off for P0 / P1.

It is **not** a fix-by deadline. A P0 with no fix available
upstream can be triaged on time by documenting the workaround +
escalating to the maintainer.

## 2. Advisory sources

Three feeds in order of precedence, lowest-latency first:

### 2.1 RustSec advisory database

- Canonical Rust-ecosystem advisory feed:
  <https://rustsec.org/advisories/>.
- Surfaced by `cargo audit` (this repo's pinned dev-dep) and
  `cargo deny check advisories`. Both read the same upstream
  feed but apply different filtering (audit = vulns only; deny
  also surfaces yanked, unmaintained, unsound).
- Skycot wraps both behind `argo security audit` (§4).

### 2.2 GitHub Security Advisories (GHSA)

- Repo-scoped advisories at
  <https://github.com/skycot/argo/security/advisories>.
- Generated by Dependabot from upstream OSV data + manual
  reports filed by the security team.
- Covers JS / web-asset dependencies the Rust audit chain
  cannot see (e.g. SPA bundle).
- Operators rely on the GitHub UI for triage of GHSA-IDs that
  do not appear in RustSec.

### 2.3 NVD / vendor feeds

- <https://nvd.nist.gov/> is the slowest feed but the
  authoritative source of CVE-IDs and CVSS v3.1 scores. When a
  RustSec advisory carries only an `RUSTSEC-` identifier, look
  up its mapped CVE in the NIST DB before the triage clock
  starts.
- Vendor-specific advisories: OpenSSL, libgit2, anything
  shipped via `-sys` crates. Subscribe security@ to the
  upstream announce list per vendor.

## 3. Named owners and escalation

Defaults are listed in §1. The override pattern works as
follows:

- **Per-vertical override.** A vertical template may declare
  `vertical.toml § [security] owner = "..."` to redirect any
  advisory that touches one of its declared crates. Defaults to
  the table in §1.
- **Per-tenant override** (post-v1). Operators may flip the
  default owners via the same TOML keys in their
  per-tenant override file.

If the default owner is unavailable, escalation order:

1. Direct backup (paged via PagerDuty `security-secondary`).
2. CTO (P0 only — paged after 30 min of unacknowledged P0).
3. Cross-vertical eng-lead-on-rotation (P2 / P3 fallback).

A P0 / P1 always has a named human owner within 15 minutes of
acknowledgement; the row stays acknowledged-but-unowned for no
longer.

## 4. The `argo security audit` CLI

`argo security audit` is a thin wrapper around `cargo audit` and
`cargo deny check advisories`. It exists so operators get a single
machine-readable envelope to consume in dashboards, alerting, and
cron-driven sweeps — without having to know two upstream tool
output shapes.

```bash
# Standard run: emit pretty-printed JSON, exit 0 if no
# unmitigated vulns above floor, 1 if anything found, 2 on
# tooling error.
argo security audit

# Filter out anything below `medium`. Useful in cron — pair with
# a low-severity weekly sweep + a high-severity continuous sweep.
argo security audit --severity-floor medium

# Compact JSON (one line) for piping into jq / ops dashboards.
argo security audit --compact
```

### 4.1 Output envelope

```json
{
  "vulnerabilities": [
    {
      "advisory_id": "RUSTSEC-2024-0003",
      "severity": "high",
      "affected_crate": "hyper",
      "fixed_in": ">=0.14.30",
      "status": "unmitigated",
      "mitigation_note": null
    }
  ],
  "total_count_by_severity": {
    "critical": 0,
    "high": 1,
    "medium": 0,
    "low": 0,
    "unknown": 0
  }
}
```

- `vulnerabilities[]` is filtered by `--severity-floor`. Rows
  below the floor are still counted in `total_count_by_severity`
  but excluded from the list.
- `status` is one of `unmitigated` / `mitigated` / `wontfix`.
  v1 reports everything as `unmitigated`; future versions read
  the override table in `argo.toml § [security.mitigations]` to
  flip rows.
- `mitigation_note` is a free-text rationale recorded alongside
  a `mitigated` / `wontfix` flip in the override table.

### 4.2 Exit codes

- **0** — no unmitigated advisories at or above the floor.
- **1** — one or more unmitigated advisories at or above the
  floor. Caller (cron / CI / on-call dashboard) should page or
  open a ticket.
- **2** — tooling error (cargo audit / cargo deny missing,
  network failure pulling the RustSec feed, malformed JSON
  output). Distinguishable from a clean / dirty audit so
  monitoring can alert on the *tooling* without alerting on
  every finding.

### 4.3 When to run it

- **Continuous (gated).** CI runs `argo security audit
  --severity-floor high` on every PR. A non-zero exit blocks
  merge.
- **Daily sweep.** `cron` runs `argo security audit
  --severity-floor low --compact` at 06:00 UTC and pushes the
  envelope to the ops dashboard. Pair with the
  `audit-key-age` cron from the key-rotation workflow so
  operators see security signals in one place.
- **Ad-hoc.** Operators run it from the workspace shell when
  reviewing a dependency upgrade or after pulling main.

## 5. Mitigation patterns

Once an advisory is triaged, the fix path falls into one of four
patterns. Document the chosen pattern in the override table so
future operators inherit context.

### 5.1 Direct version bump

Most common. Upstream has released a patched version.

```bash
# Replace the offending crate version in Cargo.toml.
cargo update -p <crate>@<old> --precise <new>
cargo audit                          # verify the row disappears
argo security audit                  # verify the envelope is clean
```

Open a single PR titled `security: bump <crate> to <new>
(RUSTSEC-YYYY-NNNN)`. The PR body cites the advisory + records
the before/after `argo security audit` envelope.

### 5.2 Workaround / config flag

The fix landed upstream but is gated behind a feature flag, or a
config change disables the vulnerable code path. Document the
config in `argo.toml § [security.mitigations]` so the row flips to
`mitigated` and stops counting against the SLA:

```toml
[security.mitigations]
"RUSTSEC-2024-0003" = { status = "mitigated", note = "TLS disabled via --insecure-bind; vulnerable code path not exercised" }
```

### 5.3 Risk accept

The advisory does not apply (false positive, unreachable code,
dev-only crate) or fixing it costs more than the risk. Flip the
row to `wontfix` with a sign-off:

```toml
[security.mitigations]
"RUSTSEC-2024-0042" = { status = "wontfix", note = "dev-only; runtime never loads this crate. CTO sign-off: <name>, <date>" }
```

P0 / P1 risk-accepts require CTO sign-off in the note. Auditors
key on this field.

### 5.4 Vendor escalation

No upstream fix, no workaround. Open an upstream issue + bring
the conversation onto the maintainer's preferred channel. Track
the escalation as a `wontfix` with a `note = "pending upstream
<URL>; review weekly"` so the override table is the source of
truth for "what blocks closing this row."

## 6. Disclosure policy

Skycot follows a **coordinated disclosure** model.

### 6.1 Inbound (a researcher reports a vuln to us)

- security@skycot.com is the canonical inbox. PGP key + the
  SECURITY.md disclosure timeline are published at
  <https://skycot.com/.well-known/security.txt>.
- Acknowledge within 24 h.
- Internal triage tracked in the same workflow as RustSec rows:
  same SLAs, same owner table, same `argo security audit`
  envelope (private finding rows are flagged `private = true`
  in the override table; the envelope omits them from the
  default output, includes them only with `--include-private`).
- Coordinate a public disclosure date with the reporter. Default
  90 days; negotiable shorter for critical bugs already
  exploited in the wild, longer for low-severity findings with a
  complex fix.
- File a GHSA on the day of disclosure. Backfill a row to
  RustSec for crate-ecosystem-relevant findings.

### 6.2 Outbound (we found a vuln in a dependency)

- File with the upstream maintainer first. Their disclosure
  timeline takes precedence over ours.
- Once upstream publishes, mirror to our security advisory
  channel + GHSA so operators of Skycot deployments see the
  notice in the standard places.
- Customer-facing announcements go through the same
  release-notes pipeline as breaking-change announcements; never
  email-blast a CVE without a corresponding patched version
  available.

### 6.3 Public communication

Every P0 / P1 advisory the security team makes public ships
with:

1. A GHSA (machine-readable, dependabot-consumable).
2. A short blog post on the engineering blog (human-readable,
   describes the impact + mitigation).
3. A patched release tagged within the SLA window.

P2 / P3 advisories ship with just the GHSA + the patched release
notes; no blog post is required.

## 7. SOC2 / ISO 27001 evidence

Auditors typically request three artefacts:

1. **The workflow doc** (this file) — proves a documented
   process exists.
2. **The tooling output** — periodic `argo security audit
   --compact` envelopes archived to the ops bucket; each is
   timestamped and signed. The cron job that runs the audit
   logs to the audit trail (`audit_kind = security_scan`), so
   the audit chain itself is the evidence trail.
3. **The override table** — `argo.toml § [security.mitigations]`
   is the canonical record of every accepted risk. Auditors read
   it to verify the named-owner + sign-off pattern.

A fresh demo workspace generates clean evidence within one cron
cycle (24 h). For an existing workspace, point auditors at the
last 90 days of `audit_kind = security_scan` rows + the current
override table.
